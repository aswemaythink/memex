memex · authored context compression

Read intent before code.

memex is a CLI that indexes a repo’s authored intent layer, so agents read what the code is for before they read the code.

Code records what a system does. The intent layer records what it is for: a README says why a folder exists, a header says what a file is for, and a case says what is claimed and how it is proven. Whoever knew the most compresses it at the moment they knew it best, and memex walks the citations between those pieces in both directions.

Markdown files and a CLI. No server, daemon, auth, MCP, LLM, vectors or database: memex starts, reads plain files live, prints and exits. Anything with a shell can use it.

The name is Vannevar Bush’s, from 1945. The story is at the bottom of the page.

Install

From a checkout of the repo. This installs the memex binary; it is one codebase for Linux, macOS and Windows.

$ git clone https://github.com/rynwhite/memex && cd memex
$ cargo install --path . --locked

One step, for a human or an agent. It installs the binary if needed, creates .memex/, wires AGENTS.md and CLAUDE.md, and prints the atlas.

$ npx @rynwhite/memex init

Or one command per toolchain, then memex init, or a binary from GitHub Releases:

Quick start

In the repo you want to index, run memex init once. It is idempotent, never overwrites files in .memex/, and reports each action: a .memex/ store, the memex block in AGENTS.md (and an @AGENTS.md line in an existing CLAUDE.md), then memex info. Reads need no setup; only memex log needs .memex/.

$ memex init
created .memex/.gitignore
created .memex/config.json
created .memex/collections/.gitkeep
created AGENTS.md
updated CLAUDE.md

memex  /home/you/project · log store .memex/logs/
graph  1 readme · 0 headers
use    memex show <path|ref> · memex search <words> · memex log <stream> <<'EOF' … EOF

Then look around. Six verbs, each one reading the layer back one level at a time.

memex info              # where everything is, and messages for you
memex show <dir>        # README, children's one-liners, chain to the root
memex show <file>       # header, cites, cited by, chain
memex search <words>    # ranked hits, grouped by collection
memex check             # gaps: missing intent, long files, unresolved refs
memex log <stream>      # record a finding from stdin; prints its ref

memex info Where things are

The atlas: names, counts and the commands to get there, never their contents. With an agent id it also counts the messages waiting for that agent.

$ memex info --agent cook-2
memex  /repo · log store .memex/logs/
graph        48 readmes · 912 headers
collections  cases 214 · doom 41 · neo-cases 294 · perf 212
streams      impl 12 (3 new in 24h) · review 3 (1 new) · drift 5
to cook-2    2 messages → memex search to:cook-2
here         crates/namer — Namer: turns atoms into stable class names
use          memex show <path|ref> · memex search <words> · memex log <stream> <<'EOF' … EOF

memex search Find by words

Words, or filters like to:cook-2 and since:2d. One group per collection: the graph, the collections alphabetically, then the logs, so thousands of headers never drown a README. A near-miss spelling is marked [~variant]. rg still finds symbols.

$ memex search namer
readmes  (showing 2 of 2)
  crates/namer/README.md  Namer: turns atoms into stable class names
headers  (showing 5 of 31)
  crates/namer/src/hash.rs  FNV-1a over canonical atom strings  [~hashes]

  cases:NAME-001  Class names are stable across runs and platforms.
logs  (showing 1 of 1)
  impl:20261013-214107-show-chain  2h · cook-2 · feat/show  show walks hub READMEs

memex show Read it, then walk the trail

Takes a path or a ref. A file prints its header, what it cites (each with its target’s one-liner), who cites it, and the READMEs above it, nearest first. A folder lists its children. Every printed label is valid input to show.

$ memex show crates/namer/src/hash.rs --up 1

Cases: NAME-001, NAME-002

memex check Where intent is missing

For the whole repo or the paths you name: files with no header, folders with no README, files over 500 code lines, one-liners over 100 characters, unresolved references and duplicate ids. Each kind names its fix. It is a report, not a gate: it exits 0 whatever it finds.

$ memex check src
check       src · 148 files · 12 folders · 3 findings
headers     (showing 2 of 2; files with no header)
  src/a.rs
  src/b.rs
(no header): add a comment block atop the file; its first sentence states the file's purpose
cites       (showing 1 of 1; unresolved)
  src/z.rs  → NAME-404
(cites): fix the reference or remove it

memex log Hand back a ref, not a report

Reads a finding from stdin; its first non-blank line is the title. Stdout is exactly the ref, on one line. Entries are immutable and expire after three days by default (keep_logs).

$ memex log review --tag namer <<'EOF'
NAME-004..006 have no citing README
crates/namer/README.md describes stations but cites no ids; claims match NAME-004..006 by text only.
EOF
review:20261013-221530-name-004-006-have-no-citing-readme

Every list prints showing N of M and takes --limit. --json makes stdout one JSON document, errors included. Exit codes: 0 ok (zero hits included), 1 not found or ambiguous, 2 usage error, 3 environment error.

The intent layer

Two parts, tied together by citations. The graph sits on the tree and is found by where it is: a README per folder, a header per file. Dimensions cut across the tree and are found by what they are: any Markdown file joins a collection with one frontmatter line, memex: <name>. Logs are the time dimension.

Cite, don’t copy

Write ids, paths and refs; memex derives the links both ways. There are no mapping files. Citations inside fenced code are ignored, and an explicit ref that resolves to nothing is listed as unresolved.

WriteLinks to
NAME-001the doc that declares that id; prose like UTF-8 never links
PREFIX-*every declared id with that prefix
collection:idthat doc, when collection is a known collection
src/hash.rsthe file or folder it names
a Markdown linka file or folder in the repo; URLs and #anchors are not refs

Context compression

memex is authored context compression. A README compresses a folder, a header compresses a file, a case line compresses a test, a log compresses an agent’s run, and a ref compresses a hand-off. Whoever knew the most compresses it at the moment they knew it best, so nothing has to summarise it after the fact.

Patterns

Collections and log streams need no declaration, so the conventions are what matter. These are the ones that held up in practice. Write it where the next reader will look: true of the code, it goes in a header or README; true of this run, a log; a claim a test proves, a case.

Test cases memex: cases

A CASES.md with memex: cases lists test ids with their claims. Each column-0 list item that opens with a backticked id is one entry; the id is kept forever. Put the id where rg finds the test: in its name where the language allows (it("NAME-001 …")), else in a comment on it.

---
memex: cases
---
# Namer cases

## Stability
- `NAME-001` Class names are stable across runs and platforms.
  Hash input is the canonical atom string, never object identity.
  Evidence: `tests/namer_stable.rs`
- `NAME-002` Two atoms with equal declarations share one class.
memex search stable class names --in cases    # the claims
memex show NAME-001                           # claim, evidence, who cites it
rg NAME-001                                   # the test itself

Write an entry before its test exists and say so in the claim, “(planned)”. memex search --in cases with no words prints the roster, and <-0 marks entries nothing cites.

Doom hunts memex: doom

A doom agent is sent to break one module. Every hunt, break found or clean, ends in one short Markdown report: the hypothesis and the red test, then the verdict. Before hunting, the next doom agent searches the collection, so nobody spends a theory re-proving a dead end. One gap per report, named by date and slug.

# doom/2026-09-20-jettison-namer-key-order.md
---
memex: doom
module: atomic/namer
theories_spent: 2
verdict: clean-hunt
---
# Namer key order survives reordered declarations
memex search namer key --in doom             # past hunts on this module
memex search verdict:break-found --in doom   # frontmatter keys are filters
memex show doom:2026-09-20-jettison-namer-key-order

Performance verdicts perf

Every optimisation tried gets a verdict, kept or cut, with what it measured. Dead ends stay in, so a cut idea is not tried a second time. When the verdicts already live in a JSON index, a json manifest makes each entry a doc where it is, with no conversion.

# .memex/collections/perf.json
{ "name": "perf", "kind": "json", "owner": "agent-perf skill",
  "roots": ["perf"], "include": ["*.json"], "at": "/entries",
  "id": "id", "title": "topic" }
memex search parallel scan --in perf   # was this tried?
memex search verdict:CUT --in perf     # every dead end
memex show PERF-W2-HASHERS             # one verdict, its fields and who cites it

Verdicts that are Markdown files need no manifest: memex: perf in their frontmatter is enough.

Hand-off and messages --to · to:

A sub-agent logs its full report and returns one line, report: <ref>. Messages are logs with --to; recipients find them with memex search to:<id>, and memex info --agent <id> counts what is waiting. Live back-and-forth stays in the harness’s own messaging.

$ memex log impl --agent cook-2 --to orchestrator <<'EOF'
show walks hub READMEs
`show <file>` now lists "cited by", through crates/README.md.
EOF
impl:20261013-214107-show-walks-hub-readmes

$ memex search to:orchestrator
logs  (showing 1 of 1)
  impl:20261013-214107-show-walks-hub-readmes  2m · cook-2 · feat/show  show walks hub READMEs

Check intent against code drift

  1. Run memex show <dir>, then read the code it describes.
  2. For each claim: does the code do it? Is there a cited case that proves it?
  3. Run memex check <dir> for unresolved citations, missing headers and missing READMEs.
  4. Fix the README, header or collection doc in the same change, or, if it’s out of scope, log the mismatch to drift.
$ memex log drift --tag namer <<'EOF'
crates/namer/README.md claims collisions are kept apart; no case proves it
EOF

When you change code, update the header or README you invalidated in the same commit, put the id in each new test, then run memex check <paths> and fix what it lists.

Promote a stream

Logs are scaffolding: useful for a couple of working days, then pruned. When a stream has proven durable, copy its files into the repo, add memex: <name> to their frontmatter, and give the owning skill the instructions. Name the collection apart from the stream, so --in reaches both.

$ mkdir -p docs/playtests
$ cp .memex/logs/playtest/*.md docs/playtests/
# then add one line to each copied file's frontmatter
---
memex: playtests
stream: playtest
time: 2026-10-15T09:12:40Z
---

Principles

  • Markdown files and a CLI

    No server, daemon, auth, MCP, LLM, vectors or database. memex starts, reads plain files live, prints and exits.

  • Agent-agnostic

    Anything with a shell can use it. Plugins only wrap it.

  • Conventions over configuration

    READMEs and headers are found by where they are; a frontmatter line joins a collection. Manifests exist only for structures that are not Markdown.

  • memex reads intent, rg reads code

    It never indexes code bodies, only the comment block atop a file.

  • Bounded output

    Every list prints showing N of M, and --limit works everywhere. Nothing is capped silently.

  • Logs are scaffolding; knowledge is authored

    A log expires. What is still true gets written into a README, a header or a collection doc by someone who understands it.

A feature earns its place by removing friction an agent actually hit in a playtest.

The story

The camera and the trail

In 1945 Vannevar Bush, who had run American science through the war, worried about the record: findings were piling up faster than anyone could find them again. In “As We May Think” (The Atlantic, July 1945) he imagined a desk of microfilm, two slanted screens and a keyboard, and called it the memex.

Storage wasn’t the point. The point was trails: put two documents side by side, press a button, tie them together, add your notes, and you have laid a path through the material that you or anyone you hand it to can walk later. Bush predicted a profession of trail blazers who make useful paths through the common record.

The process of tying two items together is the important thing.

Vannevar Bush, “As We May Think”, 1945

The same essay imagines a walnut-sized camera on a scientist’s forehead, photographing everything he sees. Two ideas, one essay. The camera is the one we keep rebuilding. The trail is the one that changed the world, through Engelbart, Nelson’s hypertext and the web: associations made on purpose, by someone who understood the material.

Eighty years later the flood is back, and agents produce it: logs, reports and hand-offs that nobody opens again. The industry reached for the camera: hooks that record everything, vector stores, LLMs summarising the pile after the fact. memex takes Bush’s other idea. Developers and agents are the trail blazers; citations are the trails; logs are the camera’s film, kept a couple of days and then thrown away.

The camera has always been tempting.
The trail has always been what mattered.
