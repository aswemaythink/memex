memex · authored context compression

Find the code worth reading.

memex turns your repo’s knowledge into a map agents can search. They see the whole codebase at a glance, open only the files that matter, and leave a trail for the next one.

The name is Vannevar Bush’s, from 1945. Here’s why.

Principles

  • Markdown first

    Knowledge lives in plain Markdown in the repo, versioned with the code. No server, database, vectors or LLM: memex reads the files live, prints and exits.

  • Agent-agnostic

    Anything with a shell can use it, whichever agent or human is at the keyboard. Plugins only wrap the CLI.

  • memex reads intent, tools read code

    memex indexes READMEs, headers and collections, never code bodies. For symbols, rg is already the right tool.

  • Conventions over configuration

    READMEs and headers are found by where they are; one frontmatter line joins a collection. Nothing to set up.

  • Never floods the context

    Every list says showing N of M and takes --limit, so an agent knows what it has not seen. Nothing is cut silently.

  • Logs expire; knowledge is written down

    Logs are work in progress: memex prunes old ones as new ones arrive. Whatever is still true gets written into a README, a header or a case by someone who understands it.

A feature earns its place by removing friction an agent actually hit in a playtest.

Get started

One command in the repo you want to index, for a human or an agent. It installs the binary if needed, creates .memex/, and adds a block to AGENTS.md that tells any agent to read intent before code. It is safe to repeat.

$npx @rynwhite/memex init

Coming with v0.1.0 Not published yet. Until then, install from a checkout (below).

Other ways to install

From a checkout of the repo, which works today. It is one codebase for Linux, macOS and Windows.

$ git clone https://github.com/rynwhite/memex && cd memex
$ cargo install --path . --locked

With v0.1.0: one command per toolchain, then memex init, or a binary from GitHub Releases. Every route comes from one cargo-dist release per tag.

brew install rynwhite/tap/memex
cargo install agent-memex
curl -LsSf https://github.com/rynwhite/memex/releases/latest/download/memex-installer.sh | sh
powershell -c "irm https://github.com/rynwhite/memex/releases/latest/download/memex-installer.ps1 | iex"

On Claude Code, an optional plugin carries the snippet and a start hook that prints memex info:

/plugin marketplace add rynwhite/memex
/plugin install memex@memex

After a manual install, run memex init in the repo. To uninstall, delete .memex/ and the marked block in AGENTS.md.

Context compression

memex is authored context compression. A README compresses a folder, a header a file, a case a test, a log an agent’s run. Whoever knew the most writes it, when they knew it best, so nothing has to summarise it later.

How an agent explores your codebase

Agents use the memex CLI to walk your codebase as a tree: a README at each folder, a header at the top of each file. Here two agents take turns. One wants to understand the API: the READMEs and the headers of the api files tell it enough, and it opens no code. The other is changing the schema: it finds the two files it must touch, the model and the migration, and opens only those.

The intent layer

READMEs, headers, collections and logs are the intent layer. The table runs from the most compressed at the top to the code at the bottom. READMEs and headers are found by where they are, collections by what they are, logs by when. An agent reads down it and opens code last.

The bigger picture

In a large codebase, reading the code to see the whole picture costs more context than any agent has. memex gives agents a compressed version to traverse instead: what each part does, conceptually. They still read code. They find the code worth reading faster, and make better decisions once they are there.

Trailblazing

Compression gets an agent to the right code. Trails let the next agent start where the last one stopped. Bush’s memex was built around them: a reader linked what they found into a path someone else could follow later. memex gives agents two kinds: logs for work in progress, and collections for what stays true.

Logs

Logs are how an orchestrator and its cooks, the agents it sends to do the work, talk to each other.

A cook logs what it did and what it found, and hands back a single line, the log’s ref; the orchestrator opens the full log only when it needs the detail. Reports, hand-offs and messages all travel this way, so logs fit whatever orchestration pattern your agents run. Logs are like chats: useful in the moment, stale soon after. memex prunes old ones as new ones arrive. Whatever is still true gets written into a README, a header or a collection; the rest can go.

Collections

A collection is a set of records on one topic that agents keep and search.

Each record is small and does one job: one attempt, one decision, one test. Any Markdown file joins a collection with one frontmatter line, so records live next to the work they describe.

Take performance work on an app. Every optimisation an agent tries gets a record: what it changed, what it measured, kept or cut. The next agent searches the collection before it starts. It sees what was tried, skips what failed, and goes straight to what is still worth trying.

Patterns

Collections and log streams need no declaration, so the conventions are what matter. These are the ones that held up in practice. Write it where the next reader will look: true of the code, it goes in a header or README; true of this run, a log; a claim a test proves, a case.

Test cases memex: cases

One folder per case, with one CASE.md in it. Its frontmatter says memex: cases and gives the case its id, which is kept forever; the body’s first line is the claim. The id goes in the test’s name, so rg finds it: it("NAME-001 class names are stable", …).

# tests/cases/NAME-001/CASE.md
---
memex: cases
id: NAME-001
---
Class names are stable across runs and platforms.
Evidence: `tests/namer.test.ts`
memex search stable class names --in cases    # the claims
memex show NAME-001                           # the claim and who cites it
rg NAME-001                                   # the test itself

The id field is required: without it every CASE.md would take the id CASE from its file stem. Write a case before its test exists and say so in the claim, “(planned)”. memex search --in cases with no words prints the roster, and <-0 marks cases nothing cites.

Doom hunts memex: doom

A doom agent is sent to break one module. Every hunt, break found or clean, ends in one short Markdown report: the hypothesis and the red test, then the verdict. Before hunting, the next doom agent searches the collection, so nobody spends a theory re-proving a dead end. One gap per report, named by date and slug.

# doom/2026-09-20-jettison-namer-key-order.md
---
memex: doom
module: atomic/namer
theories_spent: 2
verdict: clean-hunt
---
# Namer key order survives reordered declarations
memex search namer key --in doom             # past hunts on this module
memex search verdict:break-found --in doom   # frontmatter keys are filters
memex show doom:2026-09-20-jettison-namer-key-order

Performance verdicts perf

Every optimisation tried gets a verdict, kept or cut, with what it measured. Dead ends stay in, so a cut idea is not tried a second time. When the verdicts already live in a JSON index, a json collection file makes each entry a doc where it is, with no conversion.

# .memex/collections/perf.json
{ "name": "perf", "kind": "json", "owner": "agent-perf skill",
  "roots": ["perf"], "include": ["*.json"], "at": "/entries",
  "id": "id", "title": "topic" }
memex search parallel scan --in perf   # was this tried?
memex search verdict:CUT --in perf     # every dead end
memex show PERF-W2-HASHERS             # one verdict, its fields and who cites it

Verdicts that are Markdown files need no file in .memex/collections/: memex: perf in their frontmatter is enough.

Hand-off and messages --to · to:

A sub-agent logs its full report and returns one line, report: <ref>; the orchestrator runs memex show <ref> only when it needs the detail. Messages are logs with --to; recipients find them with memex search to:<id>, and memex info --agent <id> counts what is waiting. Live back-and-forth stays in the harness’s own messaging.

$ memex log impl --agent cook-2 --to orchestrator <<'EOF'
show walks hub READMEs
`show <file>` now lists "cited by", through crates/README.md.
EOF
impl:20261013-214107-show-walks-hub-readmes

$ memex search to:orchestrator
logs  (showing 1 of 1)
  impl:20261013-214107-show-walks-hub-readmes  2m · cook-2 · feat/show  show walks hub READMEs

Check intent against code drift

  1. Run memex show <dir>, then read the code it describes.
  2. For each claim: does the code do it? Is there a cited case that proves it?
  3. Run memex check <dir> for unresolved citations, missing headers and missing READMEs.
  4. Fix the README, header or collection doc in the same change, or, if it’s out of scope, log the mismatch to drift.
$ memex log drift --tag namer <<'EOF'
crates/namer/README.md claims collisions are kept apart; no case proves it
EOF

When you change code, update the header or README you invalidated in the same commit, put the id in each new test, then run memex check <paths> and fix what it lists.

Anti-pattern

Promoting logs into a collection

It is tempting to keep a useful stream by copying its log files into the repo and giving them memex: frontmatter. Don’t. A log is a record of one run, written in the moment; a collection is authored and curated. Copied logs bury the few true things under everything else that happened, and every agent after you has to read through it.

Distill instead. When a log holds something still true, write it once, in your own words, where the next reader will look: a README, a header, or a doc in a collection. Cite the ids, and let the log expire.

# don’t
$ cp .memex/logs/playtest/*.md docs/playtests/

# do: one line, where the next reader will look
# crates/namer/README.md
Hashes are stable across runs; see NAME-001.

The memex skill tells agents the same: distill a log, never promote it.

The verbs agents use

For reference: six verbs, the ones the memex block in AGENTS.md points agents at. memex reads the layer back one level at a time: a one-liner with search, then the document with show, then the chain of READMEs above it.

memex initSet it up once

Run it once in the repo you want to index. Safe to repeat: it never overwrites files in .memex/ and reports each action. It creates .memex/, writes a short block into AGENTS.md that tells any agent to read intent before code (and points an existing CLAUDE.md at it), and prints the atlas. Reading works without it; only log needs a .memex/.

project
$ memex init
created .memex/.gitignore
created .memex/config.json
created .memex/collections/.gitkeep
created AGENTS.md
updated CLAUDE.md
… then the atlas, as memex info prints it

memex infoWhere things are

The atlas: names, counts and the commands to get there, never their contents. It is the overview for humans and agents, and what the optional Claude Code start hook prints. With an agent id, it counts the messages waiting for that agent.

repo/crates/namer
$ memex info --agent cook-2
memex  /repo · log store .memex/logs/
graph        48 readmes · 912 headers
collections  cases 214 · doom 41 · neo-cases 294 · perf 212
streams      impl 12 (3 new in 24h) · review 3 (1 new) · drift 5
to cook-2    2 messages → memex search to:cook-2
here         crates/namer — Namer: turns atoms into stable class names
use          memex show <path|ref> · memex search <words> · memex log <stream> <<'EOF' … EOF

memex showRead it, then walk the trail

Takes a path or a ref. A file prints its header, what it cites (each with its target’s one-liner), who cites it, and the READMEs above it, nearest first. A folder lists its children. Nobody maintains a link table: citations come from the ids, paths and refs people already write, and are read in both directions.

repo
$ memex show crates/namer/src/hash.rs --up 1
=== crates/namer/src/hash.rs ===
FNV-1a over canonical atom strings.
Cases: NAME-001

cites
  cases:NAME-001  Class names are stable across runs and platforms.

cited by
  crates/namer/README.md  Namer: turns atoms into stable class names.
  impl:20261013-214107-show-walks-hub-readmes  show walks hub READMEs
  showing 2 of 2

chain
--- crates/namer/README.md
# Namer

Namer: turns atoms into stable class names. See `src/hash.rs` and NAME-001.

memex searchFind by words

Words, or filters like to:cook-2 and since:2d, over READMEs, headers, collections and logs. Results come grouped, so a README is never drowned by log noise, and each hit is a one-liner. A hit found by a near-miss spelling is marked [~variant]. rg still finds symbols; memex finds meaning.

repo
$ memex search namer hashs --limit 1
readmes  (showing 1 of 2)
  crates/namer/README.md  Namer: turns atoms into stable class names.
headers  (showing 1 of 31; [~hashes] fuzzy match on hashes)
  crates/namer/src/hash.rs  FNV-1a over canonical atom strings.  [~hashes]
cases  (showing 1 of 6)
  cases:NAME-001  Class names are stable across runs and platforms.

memex checkWhere intent is missing

For the whole repo or the paths you name: files with no header, folders with no README, files over 500 code lines, one-liners over 100 characters, unresolved references and duplicate ids. Each kind names its fix. It is a report, not a gate: it exits 0 whatever it finds.

repo
$ memex check src
check       src · 148 files · 12 folders · 2 findings
headers     (showing 1 of 1; files with no header)
  src/a.rs
(no header): add a comment block atop the file; its first sentence states the file's purpose
cites       (showing 1 of 1; unresolved)
  src/z.rs  → NAME-404
(cites): fix the reference or remove it

memex logHand back a ref, not a report

Reads a finding from stdin and prints its ref, exactly, on one line. An agent ends its run by logging the full report and returning one line, report: <ref>; the next reader runs memex show on it only when it needs the detail. Logs are immutable, and memex prunes old ones as new ones arrive. What is still true belongs in a README, a header, a case or a collection.

repo
$ memex log impl --agent cook-2 --tag namer,show <<'EOF'
show walks hub READMEs
`show <file>` now lists "cited by", through crates/README.md.
EOF
impl:20261013-214107-show-walks-hub-readmes

Every list prints showing N of M and takes --limit. --json makes stdout one JSON document, errors included. Exit codes: 0 ok (zero hits included), 1 not found or ambiguous, 2 usage error, 3 environment error.

The story

Good work was being lost, not because it was wrong, but because nobody could get back to it.

1945

Vannevar Bush ran American science through the Second World War. When it ended, what kept him up at night wasn’t weapons. It was the record. Science was producing findings faster than anyone could find them again.

In July 1945 he published “As We May Think” in The Atlantic. In it he imagined a desk: two slanted translucent screens, a keyboard, levers, and inside, on microfilm, every book, letter and note you owned. He called it the memex.

Storage wasn’t the point. The point was trails. Libraries index by alphabet and category; the human mind, Bush wrote, “operates by association.” On the memex you would put two documents side by side, press a button, and tie them together. Do it again and again, add your own notes, and you’ve laid a trail through the material: your reasoning, kept, so you or anyone you handed it to could walk it later.

Bush predicted a new profession: trail blazers, people who take delight in making useful paths through the common record.

The memex was never built. But Douglas Engelbart read the essay in 1945 as a young radar technician and spent his life on it. That became the 1968 demo that gave us the mouse and hypertext. Ted Nelson named hypertext with Bush in mind. From there, the web. Every link you’ve ever clicked descends from that desk.

The camera and the trail

The same essay also imagines a walnut-sized camera strapped to a scientist’s forehead, photographing everything he sees. Capture everything and sort it out later.

Two ideas, one essay. The camera is the one we keep rebuilding. The trail is the one that changed the world: associations made on purpose, by someone who understood the material.

Now

Eighty years later, the flood is back, and this time agents produce it. Every run writes logs, reports, notes and handoffs into folders nobody will open again. The answer the industry reached for is the camera: hooks that record everything, servers, vector stores, LLMs summarising the pile after the fact.

memex takes Bush’s other idea.

memex

memex is authored context compression: trails of intent, for humans and agents.

Code records what a system does. The intent layer records what it’s for: a README says why a folder exists, a header says what a file is for, a case says what’s claimed and how it’s proven, and a log says what an agent was trying and what it found. Whoever understood it best compresses it, at the moment they understood it. Citations become trails, and memex walks them both ways (the intent layer, above).

Developers and agents are the trail blazers. An agent that finishes a job compresses what it learned and cites what it touched; the next agent walks that trail instead of starting from zero. Logs are the camera’s film: kept a couple of days, then thrown away. What’s still true gets authored into the layer.

No server, no database, no model in the loop. Markdown files and a CLI. Because the compression was already done, by whoever understood it.

Why this matters to us

When the story came together, the reaction was goosebumps. It wasn’t the history alone. It was recognising that the thing we’d been designing for practical reasons (READMEs everywhere, headers, case ids cited in prose, logs that expire, no automated capture) was Bush’s idea all along, and that it had been the right idea for eighty years.

The camera has always been tempting.
The trail has always been what mattered.
