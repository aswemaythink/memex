# Contributing to memex

memex is a small Rust CLI. Its working rules are in [AGENTS.md](AGENTS.md), and the behaviour it must have is in [DESIGN.md](DESIGN.md). This file covers how to build, test and land a change.

## Order of change

1. **DESIGN.md.** A change in behaviour starts as an edit to [DESIGN.md](DESIGN.md), approved by a maintainer. If DESIGN.md is silent or contradicts itself, open an issue rather than guessing.
2. **Conformance case.** Pin the behaviour with a case in [tests/cases](tests/cases/README.md): an entry in the family's `CASES.md`, and a case folder with its `case.json`. Unit tests are welcome, but they do not count as pinning.
3. **Code.** Change the code, and update its header and its folder's README in the same change.

## Build and test

```sh
cargo build --locked
cargo test --locked
cargo fmt --check
cargo clippy --all-targets --locked -- -D warnings
```

`cargo test --locked` runs the conformance suite, the quality gate in `tests/quality.rs` and the self-host checks in `tests/selfhost.rs`. Tests must leave the tree clean: CI fails if they leave changes in the working tree. The opt-in stress suite and its timing budgets run with `cargo test --release --test stress -- --ignored`; see [tests/stress](tests/stress/README.md).

### Goldens

Each case has a golden transcript, `expect.txt`, which bless writes. Bless only the case ids your change touches:

```sh
MEMEX_BLESS=1 cargo test --test conformance -- <filter>
```

Read the result with `git diff tests/cases` before you commit. Bless is refused when `CI` is set, and CI fails if `MEMEX_BLESS` is set.

## Code quality

The full bar is in [AGENTS.md](AGENTS.md). In short:

- At most 365 lines per file.
- Each file opens with a `//!` header whose first sentence states its purpose.
- Each folder has a `README.md` whose first paragraph says what the folder is.
- Functions have at most 60 lines, cognitive complexity 15 and six arguments.
- No `#[allow]` or `#[expect]` in `src/`. Fix the code instead.
- Portable by construction: one `/` path normaliser, special names matched against directory listings (never `exists()`), and `cfg` code with both arms.

Run `cargo run -q -- audit <paths>` (or `memex audit <paths>` with an installed binary) on the paths you change, and fix what it lists.

## Pull requests

1. Branch from `main`. `main` is protected: changes land only through a pull request.
2. Fill in the pull request template and tick its checklist.
3. CI must pass on Ubuntu, macOS and Windows, and on the MSRV build (Rust 1.88).
4. A maintainer squash-merges the pull request.

## Releases

Every release ships one version to every channel: GitHub Releases (binaries and the shell and PowerShell installers), npm `@aswemaythink/memex`, Homebrew `aswemaythink/tap/memex`, crates.io `agent-memex`, and the Claude Code plugin's manifest. Nothing is published by hand.

1. In a pull request, bump the version in `Cargo.toml` (and `Cargo.lock`, via `cargo check`), in [plugins/memex/.claude-plugin/plugin.json](plugins/memex/.claude-plugin/plugin.json), and add a `## X.Y.Z - date` section at the top of [CHANGELOG.md](CHANGELOG.md); the GitHub release takes its notes from that section. Check with `scripts/check-versions.sh`.
2. Squash-merge it, then push the tag `vX.Y.Z` on that `main` commit.
3. The Release workflow ([release.yml](.github/workflows/release.yml), generated by cargo-dist from [dist-workspace.toml](dist-workspace.toml)) runs in this order:
   - **plan**, with **check-versions** ([check-versions.yml](.github/workflows/check-versions.yml)): fails before any build when the tag, `Cargo.toml`, `Cargo.lock`, the plugin manifest and the CHANGELOG heading disagree, and packages the crate with `cargo publish --dry-run`.
   - **build** the binaries and installers, then **host**: the GitHub release.
   - **publish**, in parallel: the Homebrew formula, the npm package, and the crate ([publish-crates.yml](.github/workflows/publish-crates.yml), which skips a version crates.io already has, so a re-run is safe).
   - **announce**, only when every publish job succeeded. A failed channel fails the run.
4. **Verify channels** ([verify-channels.yml](.github/workflows/verify-channels.yml)) runs after every tag's Release run, whatever its outcome, and fails unless crates.io, npm, Homebrew and GitHub Releases all show the tag's version (it retries for ten minutes while registries catch up). Run `scripts/check-channels.sh vX.Y.Z` locally for the same check.

The check-versions job also runs on every pull request, so a bump that misses a file fails before merge, and `dist plan` fails if `release.yml` differs from what cargo-dist generates: change `dist-workspace.toml`, then run `dist generate --mode ci`, never edit `release.yml` by hand.

**Secrets** (repository settings, Secrets and variables, Actions; how to create each is in [.env.example](.env.example)):

| Secret | Used by |
| --- | --- |
| `HOMEBREW_TAP_TOKEN` | pushes the formula to `aswemaythink/homebrew-tap` |
| `NPM_TOKEN` | publishes `@aswemaythink/memex` |
| `CARGO_REGISTRY_TOKEN` | publishes `agent-memex` to crates.io |

**When a channel fails**: fix the cause (usually an expired token), then re-run the failed jobs of the Release run; the crates.io job skips a version that is already up, and npm and Homebrew refuse or no-op a duplicate. Then run Verify channels by hand with the tag. Never cut a new version to paper over a missing channel.
