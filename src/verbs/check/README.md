# check

The parts of `memex check` (design §3.5d). `../check.rs` runs the verb: it resolves the arguments to a scope, finds each kind's findings over it, and hands the summary to `render/check.rs`. `scope.rs` turns the arguments into the files and folders they name: a path is resolved by `resolve/` as `show` resolves one (design §3.1), and a glob (one holding `*`, `?` or `[`) is matched by `collections/globs.rs` with the manifest `include` rules. It also lists the corpus's walked entries for the counts and the glob matches, so no file is read. `../check.rs` loads the corpus with its head facts (`here::load_with_lines`): as the corpus reads each file with a comment family for its header, it keeps the head's size, line tally and header and license line counts, and no other verb pays for them. `counts.rs` turns those into each in-scope file's line counts (design §3.5d Lines), for `length` and `thin`: a file that its 8 KiB head holds whole is not read again, and a longer one is read past its head only, on several threads. `kinds.rs` holds the kinds, in the order of design §3.5d: `headers`, `readmes`, `length`, `one-liners`, `thin`, `cites` and `ids`. Each is one function over the context. `thin` is a pointer: it is listed with its header share, but the scope line, `nothing to fix` and the JSON `findings` leave it out (design §3.5d, R30).

Choices where design §3.5d is silent: a path outside the root names nothing, since check reads only the root it runs in; a doc label or bare id is not a path, so it names nothing either; the `headers` kind takes each candidate's length from the head the corpus read, so an empty file (zero bytes) is not a finding, and a file that could not be read is not judged; a binary file (a NUL byte in its head) is skipped, as design §2.1 says, so it is never a `headers`, `length` or `thin` entry (CHK-REFINE-04); a folder that the walk could not list is not judged for a README; a `readmes` folder is judged by the walked files under it, whatever the scope, so a folder of data alone (no file with a comment family in its subtree) needs none (R29); `cites` reads each doc in scope for itself, so two docs that share a label each give their unresolved references under it, and one that both make is listed once (CHK-REFINE-02); an `ids` finding is in scope when any of its docs is; an `ids` detail names each file once, joined by ` · `; `thin` sorts by header lines over total lines, compared as exact fractions, then by path; a file without a header is not `thin`, even at 80 lines or more; the JSON `kinds` list keeps `thin` with its items (a ruling: design §3.6 says `kinds` holds the kinds with findings, while §3.5d takes `thin` out only of `findings`).
