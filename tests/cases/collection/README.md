# collection

The collection family covers the frontmatter half of design §2.2 and the collection rules of §4.2: a Markdown file whose frontmatter holds `memex: <name>` is a doc in that collection, a file whose column-0 items open with case ids is an entry index of it, and a README is the graph's, so its `memex:` key is ignored. Its prefix is `COLL`. The FRONT topic covers how the frontmatter is found (a byte order mark, CRLF line ends, a fence that never closes, the 8 KiB limit), NAME the grammar of a collection name, ONE a file that is one doc, ENTRY an entry index, PLAIN a CASES.md without the key, README the key in a README, UNREAD a Markdown file that cannot be read, CITE the citations of collection docs and entries, INFO the collections line, SHARED a collection named like the graph, a log or a stream, DUP duplicate ids, REFINE the edge cases that review found (a README past 8 KiB, an empty `memex:` value, a README's closed frontmatter), FIELDS nested and list fields, TITLE the fences that the title rule skips, and WALK which walked files are docs at all.

Each case folder holds its own fixture repo. Where design §2.2 is silent, these cases pin the choice: a `memex:` line counts only when the whole line lies inside the first 8 KiB (COLL-FRONT-06; PLAN §13 R11), and a file longer than 8 KiB is read a second time only when its key is in the head (COLL-FRONT-07). SHARED covers a collection named like the graph (`readmes`, `headers`), like `logs`, or like a log stream: it loads with one warning, keeps its own search group and resolves in `show`, while `--in` means the graph or the stream (design §4.2 Names). DUP covers duplicate ids in a collection, which `info` warns about once per id, naming each path once (design §2.2); a doc with no path (a json or folder manifest's) is named by its manifest's file (COLL-DUP-02, a ruling for PLAN §13).
